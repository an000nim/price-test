# Обновление клиентских прайсов

## 1. Вопросы до реализации

1. **Какие данные достаточны для автообновления?** Какой срок годности цены, какие площадки обязательны и сколько свежих предложений нужно по артикулу?
2. **По каким правилам меняем цену?** Откуда берётся минимальная цена для клиента, какое изменение допустимо без проверки и кто утверждает спорные рекомендации?
3. Как определяем, что предложение относится к тому же товару и сопоставимо по бренду, артикулу, упаковке, наличию и сроку доставки?
4. Какие группы товаров и клиентов взять в пилот и по каким результатам сравнения со старой системой разрешить автообновление?
5. Какой объём артикулов нужно пересчитывать за час и к какому времени новый прайс должен быть готов к рассылке?

**Почему первые два важнее всего.** Ответ на первый определит, какие позиции можно пересчитать при сбое площадки и где нужно сохранить действующую цену. Ответ на второй задаст ограничения расчёта и границу между автоматическим применением и ручным согласованием.

**Допущения.** Для пилота считаю свежими данные текущего часового запуска. Список обязательных площадок, минимальное число предложений и пороги согласуем до включения автообновления.

## 2. Архитектура

Планировщик каждый час запускает существующие парсеры в фоновом воркере, с тайм-аутами и ограниченными повторами временных ошибок по площадкам. В PostgreSQL сохраняю ID запуска, статусы площадок и предложения с источником и временем получения. Перед расчётом проверяю соответствие бренда и артикула, сопоставимость предложений, свежесть, полноту ответа и покрытие позиции. При сбое одной площадки остальные продолжают работу, а позиция пересчитывается только при достаточном покрытии, иначе сохраняется текущая цена.

Расчёт сохраняет по каждой позиции текущую и рекомендуемую цены, использованные предложения, версию правил и причину решения. В новый черновик прайса попадают только изменения с решением APPLY и вручную подтверждённые REVIEW, остальные строки сохраняют действующие цены. Уникальный ключ по ID запуска и ID прайса исключает создание второй версии при повторной обработке, а переключение активной версии выполняю транзакционно после проверки черновика и только если его исходная версия всё ещё актуальна. Действующая система формирует и рассылает прайс из активной версии.

Сначала запускаю расчёт параллельно старой системе без публикации, сравниваю цены на одинаковых входных данных и разбираю расхождения. Затем включаю публикацию для пилотной группы и слежу за долей непересчитанных позиций и резкими изменениями цен. При проблеме отключаю автопубликацию, возвращаю последнюю проверенную версию прайса и использую прежний процесс через Excel.
